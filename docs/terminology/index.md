# 术语文档

这里按**领域**沉淀面试高频术语，一篇一个方向，逐条一句话。

写这套文档的起因很实际：技术文档看得懂，但一进会议、一看别人的方案、一读 JD 就被缩写淹没。术语不通，沟通成本就会指数级上升——讨论「要做 RAG」和「我们做了 RAG 全流程」完全是两件事。

所以每篇的体例统一：**只给「术语 + 一句话释义」**，不铺陈原理。看不明白的再回头查专项资料，比一上来读长文效率高。

## 怎么查

- **按缩写查**：直接搜英文缩写（`SPU`、`CQRS`、`DPO`、`MVCC`、`GQA`），每条都带全称或中文名。
- **按场景查**：准备面试时先扫一遍对应方向，答不上来的词再展开看。
- **按对比查**：容易混淆的概念在释义里直接写清区分点（如 401 vs 403、LRU vs LFU、RAG vs 微调）。

## 术语翻译的三条约定

行业里中英混搭是常态，硬造译名反而更难沟通，因此本套文档遵循：

1. **缩写不译**：RAG、LLM、MCP、CQRS、SPU、DPO 直接说英文，不强行造中文名。
2. **专有名词不译**：LangChain、Snowflake、HNSW、Kafka 保留原文。
3. **概念词用主流译法**：Agent → 智能体，Embedding → 向量化 / 嵌入，Prompt → 提示词，Chunking → 分片。

## 一个提醒：口径比定义更重要

术语最大的坑不是「不知道」，而是「以为大家理解一样」。

以电商为例，`GMV` 含不含未付款、`复购率` 的统计窗口是 30 天还是 90 天、`ROI` 用的是利润还是收入——同一个词在不同团队能算出相差一倍的数字。所以真正专业的做法是维护一份「口径字典」，而不是靠口头约定。各领域文档里都标注了这类口径陷阱。
