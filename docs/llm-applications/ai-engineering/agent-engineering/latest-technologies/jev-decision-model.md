# Jev 决策模型调研

本笔记调研 TypeSafe AI 的 Jev / Jev 1.13（System One Model），核验日期为 2026-09-20。Jev 处于早期访问阶段，价格、速率限制与模型版本会继续变化，正文引用时应保留具体版本。

## 一、先给结论

Jev 不是 OpenAI 发布的新模型，也不是 ChatGPT 的新版本。更准确的说法是：**前 OpenAI 研究员 Diogo Almeida 创办的 TypeSafe AI 发布了 Jev，这是一个面向软件自动化的结构化决策模型**。Almeida 曾参与 RLHF、InstructGPT 等工作；TypeSafe 由他与来自 Meta/FAIR、Google Brain 等机构的成员共同创办。[TypeSafe 官方团队介绍](https://typesafe.ai/team) 与 [TechCrunch 采访](https://techcrunch.com/2026/09/18/a-new-kind-of-ai-model-from-a-chatgpt-inventor-is-thrilling-developers/)均支持这一点。

“**不生成文本，直接输出结构化判断**”基本准确，但需要补充两个边界：

1. Jev 不负责写回答、代码或解释，而是接收一段文本或 JSON 状态，回答开发者预先定义的窄问题。
2. “不产生幻觉”只能理解为**不会生成不存在的选项或 schema 外的字符串**，不能理解成“判断一定正确”。它仍然可能把输入理解错；TypeSafe 官方文档也明确说明，校准概率描述的是一组预测的长期统计关系，不保证每一次判断正确。

Jev 的核心价值不是替代通用大模型，而是把大模型工作流中的一部分判断，变成低延迟、低成本、可组合、可观察的“智能 if 语句”。适合分类、路由、风险门控、排序、审核、抽取候选项后的选择，以及对其他 LLM 的监控和校验。它不适合开放式写作、复杂多步推理、需要新文本的任务，也不能独立代替业务代码或人工审批。

## 二、Jev 到底是什么

### 1. TypeSafe 对产品的定义

TypeSafe 将这类模型命名为 **System One Models**。它借用了 Kahneman《思考，快与慢》中 System 1 的概念，强调快速、直觉式、专注的判断；复杂推理仍应交给更慢的模型或代码。[System One 官方文档](https://docs.typesafe.ai/concepts/system-one) 将其定义为：评估一个 state，并返回带类型的答案和概率。

典型输入包括：

- 客服消息、工单、邮件线程；
- JSON 格式的订单、账户、交易或 agent trace；
- 一段需要分类、评分或风险判断的文本；
- 由程序准备好的业务状态。

典型输出不是一段自然语言，而是：

- **Noul**：是/否判断，返回“为真”的概率；
- **Choice**：从开发者给定的有限选项中选一个，并返回各选项概率；
- **Score**：在有序等级上打分，并返回分布、期望分数和置信度。

例如，开发者可以提交“客户连续三天无法连接 Stripe、正在损失销售，请尽快帮助”这段 state，并定义 is_urgent、department、frustration 三个问题。Jev 返回的可能是“紧急概率 0.999、技术团队概率 0.85、挫败程度 1.0”等结构化字段，而不是写一封客服回复。[LangChain 的 Jev 集成文章](https://www.langchain.com/blog/building-a-harness-with-jev) 展示了这一调用方式。

### 2. 它与普通 LLM 的根本区别

| 维度 | 普通聊天/推理 LLM | Jev / System One |
|---|---|---|
| 主要目标 | 生成符合人类偏好的文本或完成推理 | 为软件提供窄问题的结构化判断 |
| 输出 | 任意字符串，通常还要解析和校验 | 预先定义的 Noul、Choice、Score |
| 选择空间 | 模型可能生成 schema 外的内容 | 选项由调用方定义 |
| 采样方式 | 通常逐 token 自回归生成 | 官方称对独立问题并行评估 |
| 不确定性 | 即使被要求给概率，也可能不稳定 | 返回概率分布；Choice/Score 另有 confidence |
| 工作流控制 | 模型常常决定下一步动作 | 代码保留控制流和副作用 |
| 最适合 | 对话、写作、代码、开放式推理 | 分类、路由、筛选、守门、审核、排序 |
| 不能做什么 | 并非所有 LLM 都擅长严格结构化 | 不生成回复、代码和解释，不适合开放式生成 |

官方文档对这种架构的表述很明确：**代码负责确定性工作、流程控制和副作用，模型只在需要“可编程常识”或理解非结构化数据的位置出现**。[How to build with System One](https://docs.typesafe.ai/concepts/how-to-build-with-system-one) 将其与传统软件和自主 agent 区分开来。

## 三、技术机制：为什么不输出文本会更快

### 1. 输出契约被提前限定

普通 LLM 的输出空间是语言 token 的组合，模型需要逐 token 生成，应用还要把文本解析成 JSON、枚举值或工具参数。Jev 的做法是：开发者在请求中直接声明问题类型和可接受答案空间。

请求可以包含 state、model 和 questions。每个问题有 type、instructions 和 criteria。Choice 只能在给定选项中选一个；Score 使用有序等级；Noul 只返回一个真值概率。应用拿到的结果可以直接进入代码分支，而不必从自然语言中猜测模型意图。

### 2. 多个问题可以并行

Jev 的模型和 API 设计允许在同一个 state 上同时提出多个独立问题。LangChain 的说明称，这些问题会并行评估，增加问题数量主要增加问题描述的输入 token，通常不会像多次调用 LLM 那样线性增加端到端延迟。

这对以下场景很重要：

- 一个工单同时判断紧急性、部门、情绪和是否涉及退款；
- 一条 agent trace 同时检测越权、提示注入和工具风险；
- 一批文档同时做多维评分；
- 对多个候选项批量打分，再由代码排序。

### 3. RLCD：面向校准决策的训练目标

TypeSafe 将其训练方法称为 **Reinforcement Learning for Calibrated Decisions（RLCD，校准决策强化学习）**。官方 AI primer 将 RLCD 与 RLHF、RLVR 区分：

- RLHF 优化人类更喜欢的回答；
- RLVR 优化可验证任务的正确结果；
- RLCD 优化决策及其概率，使较高概率在大量样本上对应较高的真实正确率。

校准并不等于确定性。比如，若一组预测都被标为 0.8，理想状态是在这组预测中约 80% 正确；单个返回 0.8 的样本仍可能错。[TypeSafe Confidence 文档](https://docs.typesafe.ai/confidence) 建议按风险设置阈值：低置信度转人工或更强模型，中等置信度谨慎处理，高置信度才自动执行。

### 4. “不会幻觉”的准确含义

Jev 的结构化输出具有两层约束：

- 对 Choice，只能从调用方提供的选项中选择；
- 对 Score，只能在调用方提供的有序等级上给分；
- 对 Noul，只能返回一个真值概率。

因此，它不会像普通 LLM 那样凭空生成一个不存在的部门名或工具参数。TypeSafe 称其“不会产生类型错误”，这在接口层面是成立的。

但约束答案空间并不能防止语义判断错误。开发者若定义了错误选项、问题含义有歧义、输入缺少关键上下文，或者模型误读状态，Jev 仍会在错误的问题或错误的选项空间中做出一个“合法但不正确”的判断。官方的 [Jev 1.13 jaggedness 文档](https://docs.typesafe.ai/model-jaggedness/jev-1.13) 还记录了不同问题形式之间不一定保持结构一致的边界情况。

## 四、当前公开规格与接入方式

截至本报告日期，官方模型页列出的 Jev 1.13 规格如下：

| 项目 | 公开信息 |
|---|---|
| 模型 | jev-1.13.0；别名 jev-latest |
| 输入 | 文本、JSON 对象或文本数组；暂不支持图片、音频、视频 |
| 上下文 | 64k tokens/request；state 加最长问题不超过 32k |
| 价格 | $0.042 / 百万输入 tokens；输出 token 免费 |
| 接口 | POST https://api.typesafe.ai/v1/systemone |
| 典型延迟 | 官方称多数查询约 100ms；发布文章给出 70–500ms |
| 速率限制 | 官方模型页显示 250,000 tokens/s、1,200 requests/min，且会动态调整 |
| 语言 | 英语效果最好；包括中文在内的其他语言应使用自己的数据测试 |
| 数据训练 | 官方称不使用客户请求或响应训练模型 |
| 版本管理 | jev-latest 会随新版本移动；对阈值敏感的生产系统应记录返回的版本或固定版本 |

OpenRouter 的公开页面也列出了 Jev 1.13，并显示它走专门的 Decisions API，而不是普通 chat completions 接口。[OpenRouter 模型页](https://openrouter.ai/typesafe/jev-1.13) 提供了另一套可核对的价格、上下文和调用示例。生产系统不应只依赖 latest：当模型更新后，概率分布和阈值行为可能发生变化，应该记录模型版本并重新评测。

## 五、官方性能主张应如何理解

### 1. “快 40–200 倍、便宜约 400 倍”不是所有任务的普遍结论

TypeSafe 发布文章称，Jev 在 System One 形状的任务上，相对可比的前沿 LLM 可达到约 40–200 倍速度；其公开 workflow evals 页面进一步给出约 193.6 倍速度、444.6 倍成本差距。这些数字来自 TypeSafe 自己设计的四类工作流和特定模型配置，不是一个覆盖所有任务的统一行业基准。[官方发布文章](https://typesafe.ai/blog/introducing-system-one-models-and-jev) 对测评条件做了重要限定：

- 任务先被拆成多个窄问题，代码负责组合和最终动作；
- 参考答案取 GPT-6 Astra 与 Claude Fable 5.1 的平均结果；
- 其他模型通过 TypeSafe 的 wrapper 被约束成同样的结构化决策格式；
- 工作流由 TypeSafe 能力团队设计，存在潜在设计偏差；
- 公开页面中的价格、延迟是测试时配置，不保证所有地区和高并发条件都一样。

更严谨的表述是：**在适合拆解为有限结构化判断的自动化工作流中，Jev 展现出很强的成本和延迟优势**。不能据此推出它在写作、编码或复杂推理上比大型 LLM 快 200 倍。

### 2. 公开评测显示优势与短板并存

TypeSafe 的 workflow evals 页面展示了四类示例：Security Incidents、Agent Trace Observability、Invoice Processing、Customer Service。页面说明所有模型都使用相同的工作流，Jev 的成本和时间通常很低；但在不同任务上的准确率并不总是最高。例如，页面显示 Jev 在 Customer Service workflow 上约 76.0%，而某些大型模型可达到更高；在 Invoice Processing 上 Jev 约 61.8%，明显存在任务差异。[公开评测页](https://evals.typesafe.ai/) 的正确解读应是“更适合速度和成本敏感的结构化判断”，而不是“全面超过所有 LLM”。

### 3. 外部早期使用反馈

TechCrunch 报道了几个早期案例：

- Vercel 工程师将一个用于命令安全审查的 LLM classifier 替换为 Jev，报告称速度快 5–18 倍且准确率更高；
- Bryo AI 对业务邮件分类的测试中，Gemini 略准确，但成本高 10–20 倍；该团队特别看重 Jev 返回的概率；
- Jev 发布后短时间内需求过大，TypeSafe API 曾出现服务能力不足。

这些是早期案例和媒体采访，不是独立、可复现的全面基准。它们能说明产品吸引力和潜在收益，但不应直接当作企业上线 SLA。

## 六、最有价值的应用场景

### 1. 模型路由

先用 Jev 判断请求是简单查找、抽取、局部修改，还是需要架构设计、复杂调试，再选择便宜模型、强模型或人工。路由本身如果使用大模型，会把节省的成本重新花掉；Jev 适合承担这个轻量判断。

### 2. Agent 工具调用风险门控

在工具真正执行前，使用 Noul 或 Choice 判断是否涉及删除、转账、发布、外发邮件，是否可能是提示注入或越权请求，以及是否需要用户确认。LangChain 已展示 AutoModeMiddleware 这类集成模式。不过，安全门控仍必须有硬编码的拒绝规则和审计日志，不能把 Jev 作为唯一安全边界。

### 3. 客服和工单分流

可以一次判断紧急程度、部门、客户情绪、是否退款、是否重复扣款等，再由代码分派队列。它可以降低每条消息的成本，也比从生成文本中正则提取字段更容易稳定运行。

### 4. RAG 和搜索后处理

对检索到的段落做相关性、是否包含答案、是否含提示注入、是否与问题矛盾等判断；再决定哪些片段进入生成模型。官方文档提供了 RAG passage classification、重排序和语义查找等 cookbook。

### 5. LLM 输出审查和可观测性

Jev 可以检查另一模型的轨迹、工具调用、引用是否被原文支持、输出是否存在风险。它不需要再次生成长文本，因此适合高频、低成本的监控层。

### 6. 大规模数据特征化

在大量邮件、日志、文档、记录上生成低维结构化特征，再交给传统机器学习、规则系统或数据仓库使用。这里的关键不是“让模型写摘要”，而是把非结构化数据变成可排序、可聚合的判断信号。

## 七、局限、风险与工程取舍

### 1. 任务必须先被正确拆解

Jev 的优势建立在“问题空间已经被定义”的前提上。若把多个判断塞进一句宽泛问题，如“这封邮件是否恶意”，结果难以解释、难以调阈值。官方建议将其拆成是否索要凭证、是否制造时间压力、是否伪造组织身份、是否包含异常奖励等原子问题。

拆解带来工程成本：团队需要维护问题定义、选项描述、边界样例、阈值和组合逻辑。Jev 不是把复杂性消失了，而是把一部分复杂性从 prompt 和 agent 循环转移到了工作流设计。

### 2. 概率需要校准和持续监控

高概率不是单个样本的正确保证。上线前至少需要：

- 用真实历史数据做分层评估；
- 绘制 reliability diagram 或计算 Brier score、ECE；
- 分别评估高风险和低风险类别；
- 记录模型版本、问题定义、输入摘要、概率和最终人工结果；
- 设置“自动执行、复核、拒绝/升级”三段式阈值；
- 版本更新后重新校准阈值。

### 3. 结构化输出不等于无幻觉

Jev 不会返回 schema 外的字符串，但可能在 schema 内选择错误类别。对付款、删除、账户权限、医疗或合规场景，必须增加确定性校验、二次确认和人工兜底。

### 4. 上下文过多会伤害准确率

官方 jaggedness 页面明确提醒，Jev 会受到 context rot 影响：state 中放入与问题无关的内容会降低准确率。工程实现需要先做上下文裁剪，只提供本问题需要的记录和依据。

### 5. 语言和模态限制

目前公开模型主要针对英文训练，图片、音频、视频不能直接输入。中文业务要用自己的样本测试，不能直接套用英文阈值。多模态应用需要先用 OCR、ASR、视觉模型或业务解析器把输入转成文本或结构化字段，这会引入额外延迟和误差。

### 6. 版本、服务和供应商风险

jev-latest 会移动；官方速率限制正在动态调整；产品仍处于早期访问阶段。企业应固定版本并保留 fallback，对 API 超时、429 和服务中断设计降级，保留普通 LLM、规则系统或人工通道，评估数据保留、区域、合规和零数据保留条款。

### 7. 不是所有问题都适合 System One

以下任务通常应继续使用生成或推理模型：

- 写客服回复、报告、代码和解释；
- 需要发现未知类别；
- 需要多步计划、反事实推理或长链条证明；
- 需要从候选集之外生成新值；
- 需要处理图片、音频或视频，而没有可靠的预处理链路。

## 八、与传统方案的选型建议

| 需求 | 首选 | Jev 的位置 |
|---|---|---|
| 纯规则、字段完整、逻辑稳定 | 传统代码/SQL | 不应调用模型 |
| 有限类别分类、需要理解自然语言 | Jev | 直接输出 Choice |
| 是/否风险判断 | Jev + 阈值 + 兜底 | 输出 Noul |
| 有序严重性、情绪、质量评分 | Jev Score | 同时读取分布和 confidence |
| 需要写文本或代码 | LLM | Jev 可做路由/审核 |
| 复杂多步推理 | 推理型 LLM | Jev 可做前置筛选或后置检查 |
| 高风险自动动作 | 规则 + Jev + 人工 | 不应只依赖 Jev |
| 图片、音频、视频 | 多模态模型 | Jev 只处理预处理后的文本状态 |

一个比较稳妥的生产组合是：

1. 代码先做确定性检查；
2. Jev 做有限、原子、可解释的判断；
3. 代码依据概率和业务风险组合结果；
4. 低置信度交给人工或强模型；
5. 需要生成内容时，再调用通用 LLM；
6. 用日志和离线样本持续校准。

## 九、建议的试点方案

如果要评估 Jev 是否适合自己的项目，不建议直接从高风险动作开始。可以按下面顺序做一个两周左右的离线试点：

### 第一步：选择一个可量化任务

优先考虑工单分流、邮件分类、RAG 片段筛选、agent trace 风险标注等任务。要求有历史数据和人工标签。

### 第二步：定义原子问题

将一个大判断拆成 3–10 个 Noul、Choice 或 Score。每个问题只表达一个维度，选项使用具体场景描述，避免“低/中/高”这种没有语义的等级。

### 第三步：建立三方对照

同一批数据比较规则系统、当前使用的 LLM、Jev，以及必要时的 Jev + LLM 级联。同时记录准确率、召回率、校准误差、P50/P95 延迟、每千条成本和人工复核率。

### 第四步：设置风险阈值

高置信度且低风险自动执行；中等置信度进入复核队列；低置信度或高风险进入人工或强模型；不在预设选项空间的情况直接升级，而不是强行归类。

### 第五步：验证中文和领域数据

至少按语言、行业、客户类型、长短文本、边界样例分层。重点检查中文、代码混杂、表格化 JSON、讽刺表达和缺少上下文的输入。

### 第六步：固定版本并保留降级

生产请求记录返回的版本号，不要只记录别名。为 429、超时、模型更新和概率漂移准备 fallback。

## 十、最终判断

Jev 值得关注的地方，不是“又出现了一个更小的 LLM”，而是它提出了不同的产品接口：**让模型成为软件中的概率型判断函数，而不是试图成为一个会说话的万能 agent**。

这个方向解决的是当前 AI 自动化中的一个真实问题：许多程序其实不需要一段完整回答，只需要知道“是否紧急”“该走哪个分支”“这个工具调用是否危险”“哪个候选更相关”。用通用 LLM 解决这些问题，往往要承担文本解析、额外延迟、输出漂移和成本；Jev 将答案空间、控制流和风险阈值更多地交还给代码。

但它的成功条件同样严格：任务要能拆成有限问题，开发者要愿意设计和维护 workflow，数据要支持校准，业务要允许低置信度升级。Jev 不是通用大模型的替代品，也不是“不会犯错的 AI”。更准确的定位是：**面向自动化软件的快速结构化判断层，可作为规则系统和通用 LLM 之间的一层智能基础设施**。

对于已有 agent、客服路由、内容审核、RAG 和自动化平台的团队，最合理的行动是做一个可回放、可量化、低风险的离线试点；对于主要需求是写作、代码生成或复杂推理的团队，Jev 暂时不应成为主模型。
